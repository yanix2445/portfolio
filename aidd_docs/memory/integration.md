# Integration

Comment le site s'intègre aux services externes. La carte de tous les outils se trouve dans `ecosystem.md`.

## External services

- **Cloudflare Turnstile** : protège le formulaire contre le spam. Le widget est côté client, la vérification côté serveur se fait via `siteverify` dans `src/lib/turnstile.ts`.
- **Resend** : envoie le mail de contact. Le domaine vérifié chez Resend est `yanis-harrat.com` (vérifié le 2026-11-16) ; `send.yanis-harrat.com` n'est que le sous-domaine de ses enregistrements DNS (SPF, rebonds), pas un domaine d'expédition. Le client est dans `src/lib/resend.ts`, avec l'adresse du visiteur en `replyTo`. L'expéditeur par défaut est `contact@yanis-harrat.com` ; `CONTACT_FROM_EMAIL` remplace cette adresse au besoin. Chaque message part en deux mails : la notification pour Yanis (`replyTo` : le visiteur), puis l'accusé de réception pour le visiteur (`replyTo` : `CONTACT.email`), qui annonce une réponse sous 48 à 72 h. Seule la notification décide du succès ; un accusé refusé est seulement loggé. L'accusé ne recopie pas le message, pour que le formulaire ne serve pas de relais de spam depuis le domaine. Les deux templates (`src/lib/contact-emails.ts`) sont en HTML à tableaux et styles en ligne, aux couleurs du site, polices système (une police web ferait appeler Google à l'ouverture), avec une version texte. L'accusé porte `Auto-Submitted: auto-generated` (RFC 3834) pour que les répondeurs d'absence n'y répondent pas. Ce sont des mails transactionnels : ni lien de désinscription ni `List-Unsubscribe`, réservés aux envois marketing ou de masse. Le suivi d'ouverture et de clics est coupé sur le domaine chez Resend (2026-11-17) et doit le rester : choix de Yanis du 2026-11-17, conforme à la recommandation CNIL d'avril 2026 sur les pixels de suivi (consentement pour toute mesure d'audience ; l'exemption « délivrabilité » ne vaut pas le coût ici). Les mails n'ont aucune image. Pour savoir si un mail est arrivé, lire son statut (livré, rejeté, signalé comme spam) dans Resend, sans pixel. DMARC du domaine en `p=reject` strict : l'expéditeur doit rester sur `@yanis-harrat.com` (DKIM `resend._domainkey` aligné). Chaque mail du formulaire porte l'étiquette Resend `contact` (`notification` ou `confirmation`) ; le webhook (`/api/resend-webhook`) n'alerte que pour ces mails, et l'alerte elle-même n'en porte pas (pas de boucle). Le webhook reçoit les événements de tout le compte Resend, autres domaines compris. Ne pas utiliser `@react-email/components`, qui est déprécié. Deux mails par message : le quota gratuit de Resend (100 par jour) couvre 50 messages par jour.
- **Vercel Analytics** : le composant `<Analytics />` est placé dans le layout racine. Il fonctionne sans cookie. Pas d'événements custom en offre Hobby.

## Calling conventions

- Les secrets restent côté serveur : `RESEND_API_KEY`, `TURNSTILE_SECRET_KEY`, `CONTACT_TO_EMAIL`, `RESEND_WEBHOOK_SECRET` (production seulement : les previews sont protégées par Vercel Authentication, Resend ne peut pas les joindre). Seule la clé de site `NEXT_PUBLIC_TURNSTILE_SITE_KEY` est exposée au client. S'il manque une des quatre variables, le formulaire n'est pas affiché. La liste des variables est dans `.env.example`.
- On n'envoie jamais de mail si la vérification Turnstile échoue.
- Si Resend ou Turnstile est indisponible, l'utilisateur reçoit une erreur générique l'invitant à réessayer plus tard. Aucune relance automatique. Les deux clients renvoient `false` pour tout échec et ne lèvent jamais. Ils importent `server-only` : un composant client qui les importerait casserait le build.
- Clés de test Turnstile (publiques, dans `.env.example`) pour le développement et les tests e2e. Aucune clé Resend n'entre dans le repo.
- RGPD : Resend (stockage aux États-Unis, rétention de 30 jours), Turnstile (intérêt légitime) et Vercel Analytics doivent être déclarés dans `/mentions-legales`. Tout nouveau service doit y être ajouté.
